# Security policy and threat model

## Reporting a vulnerability

Please report suspected vulnerabilities through this project's GitHub repository. Prefer **Security → Advisories → Report a vulnerability** for a private report. If private reporting is unavailable, open an issue asking for a private reporting channel and keep exploit details, credentials and sensitive data out of the public issue.

Every report must include a reproducible proof of concept demonstrating the issue. Include:

- The OSPMAE version or commit, deployment configuration relevant to the issue, and affected component.
- The attacker's required access, permissions and other prerequisites.
- Minimal reproduction steps or a script, expected and actual results, and evidence of the security impact.
- Synthetic test data and redacted logs or screenshots where useful.

Test on an installation you own or have explicit permission to assess. Use the smallest demonstration that establishes the issue, preserve other people's data, and avoid disruptive testing against public or hosted instances.

Our goal is to provide a preliminary response within **72 hours**. This is an acknowledgement and initial assessment target; investigation and remediation time depends on the report. OSPMAE offers **no monetary bounties**. Authors of validated reports will be credited, using their preferred name or handle, unless they request anonymity. We coordinate disclosure with reporters after assessing impact and remediation.

## Scope and trust boundaries

### What OSPMAE protects

OSPMAE stores the project catalogue: projects, releases, capability and framework mappings, manifests, dependency and vulnerability records, questions and subscriptions, plus user accounts and preferences. These records can carry an adopter's internal architecture or a maintainer's unreleased data, and several surfaces (draft releases, manifests, shared groups, subscription addresses) express who may read what. Security objectives include controlling who reads or changes each record, keeping scan credentials within their configured pipeline, preserving the integrity of dependency and vulnerability data once recorded, and maintaining service availability.

An OSPMAE installation is an organisational trust boundary. Users inside it receive access through roles, groups and permissions; project ownership (creator and owner groups) scopes writes for every role except administrator. Hosting mutually distrustful organisations requires isolated installations, databases and secrets.

### Actors

The threat model includes an unauthenticated Internet client, a malicious website visited by a signed-in user, a user acting beyond their assigned permissions, a project owner submitting hostile repository URLs or content, and hostile content returned by a configured release feed or package repository. A granted permission establishes who may act; reviewers still judge the truth of catalogue entries and scan results.

Application administrators are trusted to configure providers, permissions, feature switches and retention. Deployment operators control the executable code, database, broker and environment secrets. Compromise of these privileges can compromise the installation. An administrator's intended ability to delete data or grant permissions is part of that role; escaping the role's intended authority remains a security issue.

Upstream identity providers, Git hosts and package registries are trusted for their specific functions. A compromised provider can assert identities; a compromised Git host can return fabricated repository contents and observe the cloned content. The dependency host allowlist, per-request budgets and the scrubbed clone environment reduce the resulting exposure.

### Hostile scan inputs

A project's repository URL, lockfiles, package names, vulnerability titles and release feeds can all be attacker-shaped. The scan pipeline contains what such input can do to its own run: repository URLs validate against a host allowlist with credential and control-character refusals, clones run in a fixed scrubbed environment with redirects disabled and positional (non-option) refs only, lockfile parsing reads at most the configured bytes per file and caps traversed and matched files, feeds screen entity declarations across the whole bounded payload, one malformed lockfile or finding costs that item alone, and display values are cleaned before storage. Within those limits hostile input can still describe false dependencies or unsafe-looking findings; the catalogue marks their provenance through the recorded source files and commit, and reviewers or adopters verify before asserting anything downstream.

## Authentication

### Sessions

Browser sessions use random, server-generated identifiers stored in the database (`sessions`). The browser receives an HttpOnly session cookie with `SameSite` policy and `Secure` flag from configuration; CSRF protection pairs a separate CSRF cookie with a header check written by `security/csrf.py`. A session ends at its sliding expiry and also at a fixed time after sign-in (`OSPMAE_SESSION_ABSOLUTE_TTL_SECONDS`, 30 days by default), however recently it was used. Signing in issues a fresh identifier; signing out revokes the account's sessions.

Password sign-in follows one policy, shared with KEEN, built on NIST SP 800-63B-4 section 3.2.2 (no more than 100 consecutive failures, waits that grow towards that limit, and signals that keep the account holder signing in) and the OWASP device-cookie protocol (`security/sign_in_throttle.py`):

- **Recognised browsers.** A browser that has given an account's correct password holds an HttpOnly, Secure, `SameSite=Strict` device cookie for that account (`__Host-ospmae_device` where cookies are Secure and no cookie domain is set), valid for 90 days and replaced by a fresh one at each correct password; the database holds only its SHA-256 digest, and an account keeps its 20 newest. Its attempts for that username skip the per-address allowance and the account's throttle and draw on their own allowance: five wrong passwords in a row end its recognition.
- **Other browsers.** Attempts from any other browser draw on a per-address allowance (30 in five minutes, counting an IPv6 /64 network as one address) and on the account's throttle: the first five consecutive failures are free, each later attempt opens a wait of 30 seconds that doubles with each further failure up to an hour before the next attempt is heard, and after 100 consecutive failures other browsers are refused until a correct password from a recognised browser or a password reset. Failures are forgotten 30 days after the last one. The throttle is keyed by a digest of the compared username (compatibility-normalised, case-folded, invisible characters removed, spaces collapsed) whether or not an account has it, so its answers do not show which accounts exist; concurrent attempts take the throttle row's lock, so they cannot share one opening.
- **Refusals.** A held attempt is answered 429 with a `Retry-After` and never reaches password verification. Every other rejection (unknown, inactive or wrong password) performs one full PBKDF2 verification (260,000 iterations), against a fixed dummy hash where no usable account exists, so response timing carries no account-existence signal. A blank username refuses before any throttling or password work.
- **Recovery.** A correct password ends the account's count. A password change ends the account's other sessions and every browser's recognition; a completed password reset ends every session and every browser's recognition and clears the account's throttle.

Accepted risk. Someone who knows a username can make sign-in from browsers that have never signed in to that account wait up to an hour between attempts, and after 100 consecutive failures refuse them until recovery; the account holder's recognised browsers keep signing in throughout, and a mailed password reset clears the throttle. An attacker without a device cookie gets at most 100 consecutive password guesses per account, and one holding a stolen device cookie five more before it lapses; a correct password, which ends the count, also restarts that budget. OSPMAE accepts both: reports that sign-in from a new browser can be delayed by someone else's failures, or that the stated guess budget exists, describe this policy. A second factor covers a guessed password.

A completed sign-in, any second factor included, ends the account's earlier sessions; a correct password whose second factor is still pending ends none.

Password reset: requests answer 204 on every path with a synchronised commit shape, so wall clock separates no outcomes. Tokens are single-use, hashed (SHA-256 over a 256-bit random value) with a one-hour expiry bound to the account, and issuance is rate-limited per address (5/15 min) and per account (3/15 min). Links point at `OSPMAE_PUBLIC_BASE_URL`, which the deployment must set before mail flows start; the printed link carries the configured origin alone. Password change re-verifies the current password under a per-account allowance (5/5 min), and SSO sessions decline it.

Mailbox ownership: an account's addresses in `user_emails` begin unverified when self-asserted; `/v1/me/emails/{id}/verify-request` mails a hashed, 24-hour, single-use verification token, and `/v1/me/emails/verify` consumes it. Verified addresses are stored, and a verified email participates in SSO linking only when the identity provider also marks the address verified, so linking requires proof on both sides. Session trust never derives from `preferred_username` or other selectable provider claims.

### Passwords

Passwords hash with PBKDF2-SHA256 at 260,000 iterations and per-password salts (`security/passwords.py`). Account creation validates the username shape (letters, digits and `._-`, 1–64 characters) because usernames appear in response headers and drive the case-folded identity comparisons above. Roles arrive from the server's role model; local sessions carry their authority from the database, refreshed through the same middleware lookup as every request.

### Local second factor

Local accounts may enrol a TOTP authenticator, WebAuthn security keys/passkeys or both, backed by ten single-use recovery codes. `OSPMAE_MFA_POLICY` decides whom the ceremony demands of on local sign-in (`optional`, `admins`, `all`); a second factor on top of a correct password starts a five-minute challenge whose cookie (`ospmae_mfa_pending`, `__Host-` prefixed over HTTPS) is separate from the session cookie, expires on logout, and dies with any account change: every challenge row records the enrolment version and a digest of the password it was started for.

Every ceremony step re-decides its stage and enforces origin (`Origin` must equal `OSPMAE_PUBLIC_BASE_URL`, HTTPS except plain-localhost), per-address (40/5 min) and per-account (15/5 min) allowances, and an account-level wrong-code counter: five wrong TOTP or recovery codes reject everything for an hour, counted across sign-ins by digest. Recovery codes are stored as SHA-256 hashes and burn on use; TOTP secrets are stored Fernet-encrypted under `OSPMAE_MFA_ENCRYPTION_KEY` and verify only forward through a per-account last-step counter, so a code proves the factor once. WebAuthn verification pins the registered origin, relying-party ID and user handle, rejects cross-origin/cross-site ceremonies, and consumes its challenge in the row before any result commits, so a failed proof never leaves a replayable challenge.

Each enrolment bump increments the account's `mfa_version`; a session row whose recorded version disagrees, or which does not prove the factor while one is enabled or required, is deleted at resolution, so an enrolment change ends every other local session. SSO-created sessions are outside the local ceremony. Removing the last factor turns the enrolment off (and spends the recovery codes), and MFA-required accounts cannot remove their only factor until a replacement proves.

### Single sign-on and account linking

OpenID Connect providers configure client id/secret, endpoints, issuer, JWKS, redirect URI, allowed email domains and per-provider link/provision switches; the same rules apply to the bundled GitHub OAuth2 support. Every enabled provider requires an explicitly configured `REDIRECT_URI`; the callback address never derives from a request host. Authorisation requests use PKCE S256, single-use server-side state with a 10-minute expiry and per-browser binding, and a state row is consumed atomically before the token exchange. Token exchange validates issuer, audience, expiry, nonce and issued-at against configured sources and the JWKS keys; auto-provision places `pending` users pending administrator approval. Automatic linking matches only on a provider-verified email held by exactly one account whose `user_emails` row is verified.

### Trusted remote-user authentication

`OSPMAE_TRUST_REMOTE_USER=true` hands authentication to the configured identity header, which is honoured only when the socket peer sits inside `OSPMAE_TRUSTED_PROXY_CIDRS`, and only for the single configured header name (default `REMOTE_USER`). The supplied nginx clears the client's copies of every identity header and lets deployments that use upstream authentication supply their own proxy configuration that sets the header from the authenticating layer's output. Auto-provisioned users land `pending`.

### Sign-in notices

Ported from KEEN: every completed sign-in, local or SSO, records its client address against the account (`user_login_ips`, `services/security_notifications.py`), and the first sign-in from an address the account has not used before mails the account's notification address a "Sign-in from an unfamiliar IP address" notice naming the account, time and address. A local sign-in with a second factor counts as completed only once the factor is verified, so a password alone neither alerts nor teaches OSPMAE a new address. The account/address key is unique, so parallel sign-ins from one new address send one notice. Addresses are learned even while mail is not configured, and are kept until the account is deleted. Header-trusted remote-user requests have no sign-in step and send no notice. The table starts empty on upgrade, so each account's first sign-in from each address afterwards sends one notice.

### Mail outbox and notifications

Outgoing mail is a transactional outbox (`notifications`): senders queue inside their own transaction and the worker drains rows with exponential backoff, recording only the exception class on failure and clearing a sent message's body (verification links are one-time secrets). Bodies of spent rows are deleted after thirty days. A request's session discards what it has not committed, so mail commits with the change it reports (a reset link with its token, a new account's administrator notice with the account); a sender that reports a change already committed commits its mail itself (`tasks/notifications.commit_and_kick`). An interactive kick sends promptly when the worker is reachable; the beat schedule retries everything, so a missed kick never loses committed mail.

### Client addresses

`security/client_addr.py` resolves every client address (rate-limit keys, audit records, audit trails in the UI): it walks `X-Forwarded-For` right-to-left while each hop stays inside `OSPMAE_TRUSTED_PROXY_CIDRS` and keeps the socket peer otherwise. Allowance keys count one IPv4 address or one IPv6 /64 network per bucket, so a home or officeIPv6 subscriber stays inside its network's budget. Unset `OSPMAE_TRUSTED_PROXY_CIDRS` trusts loopback only; Compose deployments set their Compose network range explicitly. An untrusted client's forwarded headers cannot change its resolved address.

## Authorisation

### Enforcement

Routes acquire their actor through the session cookie (or trusted header after the peer check above), and pending users stay out of operational `/v1` surfaces apart from account ones. Roles (`security/roles.py`) and permissions (`security/permissions.py`) compose effective authority from the account role, group roles and granted permissions, and project ownership (creator or owner group) object-scopes every non-administrator role: a granted `project.write` widens nothing. Manifests grant read access through explicit owner/group membership, and subscription/question actions check ownership of the named objects. Administrative surfaces (`/v1/admin/*`, audit listing, user management) require the admin role, and the last active administrator resists demotion, deactivation, deletion and access stripping from every supported path.

Feature switches (`core/features.py`, ported from KEEN) turn optional areas off at the router level (HTTP 404), in Celery tasks (no-op when they run) and in startup seeding, so a disabled install behaves like a small application: authentication, accounts, the project catalogue and the dependency/vulnerability dashboard stay, everything else answers 404. Administrators change them on the Administration page; each save is checked against the stored configuration version under a row lock (a stale save answers 409) and every version is kept as a revision naming who saved it. The deployment's `OSPMAE_FEATURE_*` settings are a ceiling the page cannot raise. Every request reads the stored version, so all API and worker processes apply a change at once.

### Scanning and dependencies

Dependency discovery enqueues per project version from explicit operator or project-owner actions; the `dependency_discovery` host allowlist (`OSPMAE_DISCOVERY_ALLOWED_HOSTS`, github/gitlab/codeberg by default) bounds clone destinations together with the URL validations above; clones cap their duration (`OSPMAE_DEPENDENCY_DISCOVERY_CLONE_TIMEOUT_SECONDS`) and traversal (`OSPMAE_DEPENDENCY_DISCOVERY_MAX_FILES`, `OSPMAE_DEPENDENCY_DISCOVERY_MAX_FILE_BYTES` per file), running grype/syft with configured paths and budgets. Discoveries exclude `.git`, build and vendored directories from traversal, skip symlinks, and clean displayed names/titles. Vulnerability records replay only through the recorded scanners; results stored for one version never name managed secrets, and clone errors echo credentials redacted (`redact_url`).

A project that tracks a branch names it under the git ref-name rules (`depscan.scan.validate_git_ref_name`, which every ref reaching `ls-remote` or `clone` passes, a leading `-` included in its refusals), and its repository URL takes the same validation as version source links. The scan clones exactly that branch head, and a branch missing from the remote fails the scan with an error. Re-scans of one project run at most hourly; the beat poller claims each project through a compare-and-set on its last poll time, so overlapping beats queue a branch once.

A private repository's clones authenticate with one access token per project (`security/repo_credentials.py`). The token is write-only: the API stores it Fernet-encrypted under a key derived with HKDF from `OSPMAE_MFA_ENCRYPTION_KEY` for this purpose alone (so a stored TOTP secret and a stored token cannot stand in for one another), reports only whether one is saved, and keeps it out of responses, changelogs (which record only when a token was saved), audit rows and error text. Each token is bound to the host it was entered for, which must pass the clone host allowlist; changing the host needs the token entered again, and making the repository public deletes it. Git receives it only as an `Authorization` header scoped to `https://<host>/` through `GIT_CONFIG_*` environment entries, never in a command line or URL, so it is never sent to another host or over plain HTTP; a source URL elsewhere fails the scan before git runs. Anyone who can edit the project can point its scans at another repository on the same host, so tokens should be read-only and scoped to the repositories the project needs. Without a valid key, saving a token is refused; after the key changes, scans of private repositories fail until the token is entered again.

Release feeds fetch one bounded body per project on each beat poll, following redirects only after re-validating each hop against the private-network screen, rejecting non-HTTPS schemes, applying size/time limits and reading entity-free XML only. Release feed-derived versions inherit capability mappings only from existing published versions of the same project, cap 10 new versions per cycle, and stay consistent with the subscription notifications the project owner configured.

## Browser boundaries

### CSRF, Origin and WebSockets

Every unsafe request (POST, PUT, PATCH, DELETE) from a browser must come from OSPMAE's own origin: with `OSPMAE_PUBLIC_BASE_URL` set, `Origin` must equal it (scheme, host and port); without it, the `Origin` host must equal the request's `Host`. Clients that send no `Origin` (scripts, curl) pass this check unless they report `Sec-Fetch-Site: cross-site`. The origin check also covers the writes made before anyone is signed in (signing in, password resets, a second factor in progress), which have no CSRF token yet. Every signed-in unsafe request apart from the sign-in form itself also requires the CSRF header matching the CSRF cookie, compared in constant time, whether the account came from a session cookie or a trusted identity header; browsers signed in by a trusted proxy receive the CSRF cookie with their first signed-in response. Browser pages read the CSRF cookie themselves for header injection; the navbar POST/logout flow sends the token as a parameter, and a session-destroying `GET /v1/auth/logout` without matching proof leaves authentication untouched and lands the browser on a harmless page. WebSocket handshakes require an `Origin` passing the same check, complete authentication, and close 4401/4403/4429 on failure; per-account connection caps (8) and per-client-address handshake allowances (30/min, by resolved client address, so clients behind the proxy do not share one) bound connection churn, and the authentication database session closes at the end of the handshake, spanning no idle connection.

### Request limits

`security/request_limits.py` (ported from KEEN; keep them aligned) reads each request body in full before any middleware or route sees it, so a handler never commits data ahead of an oversized tail: credential forms take at most 16 KiB, second-factor ceremonies 256 KiB, and everything else 2 MiB; a body not received within 30 seconds is refused (408). JSON bodies must be standard JSON with finite numbers, at most 64 levels of nesting, at most 20,000 values and no NUL characters (which PostgreSQL text cannot hold). Request targets carrying NUL, `.`/`..` segments or encoded `/` or `\` are refused, since a crafted identifier could otherwise steer a page's own authenticated request to another route. Validation errors name the invalid fields without echoing submitted values, which can be credentials. The middleware that loads the signed-in account runs its database work in the thread pool and closes its session before the route runs, so no request holds a connection for its whole length.

### Rendering, links and navigation

First-party JavaScript renders untrusted text through `escapeHtml`/`textContent`; links run through `safeExternalHref` in the design system and `safeHref` in OSPMAE pages, which drop script, data and forbidden schemes, protocol-relative URLs, backslashes and control characters. Post-authentication destinations (`?next=`, logout redirects, stored navbar shortcuts) validate through one shared helper (`security/url_safety.py safe_relative_route_path`) on both server and client, refusing absolute URLs, `//host`, backslashes and control characters. Markdown export escapes cell text with pipe rules and serves as `text/markdown` attachment; CSV/XLSX exports tabulate with formula-prefix neutralisation (leading `=` `+` `-` `@` and `Tab`) and `attachment` dispositions.

### Request paths through the proxy

The supplied nginx configuration adds the security-header set (X-Content-Type-Options, X-Frame-Options, referrer policy, COOP, HSTS and a `default-src 'self'` CSP) unless the upstream already set one, carries the cache-policy map (immutable vendored assets, fresh HTML and first-party scripts), redirects with relative paths (`absolute_redirect off`), and refuses `//`-prefixed request targets so browsers keep the installation's own origin in echoed paths. The API proxy clears the client-supplied identity headers on `/v1/` and `/ws/`, and websocket upgrades keep their separate connection policy and idle timeout.

### Downloads, exports and caching

Exports (markdown manifest, XLSX/CSV comparison and dependency downloads, PDF report generation in the browser) stream as attachments with fixed, escaped names and carry no secrets beyond what the caller may read. Vendored assets serve immutable cache lifetimes keyed by exact URL paths, which lets a build revision replace their content. JSON API responses carry content types from the framework without HTML rendering at the API layer.

## Background work

Celery workers process scans, release feeds, tracked-branch re-scans (an hour apart at the shortest) and maintenance sweeps with per-task budgets: clone timeouts, per-file byte caps, per-feed size and time limits, and a beat-scheduled sweeper that deletes expired login states, used/expired reset and verification tokens, aging rate-limit ledger rows and audit rows past `OSPMAE_AUDIT_LOG_RETENTION_DAYS` (90 by default). The git subprocess environment holds the credentials layer of its own path; clone children run with prompts, askpass helpers, system and global git configuration and HTTP redirects disabled, and the workers in general receive only the environment variables their configuration names. Release-feed ignore patterns are written by project editors and searched against text from upstream feeds, so regular expressions are refused when saved, and skipped when run, unless their backtracking stays bounded (`security/regex_shape.py`, ported from KEEN's pattern checks): no unbounded repeat inside another repeat, no unbounded repeat of anything wider than one character unless possessive (`*+`, `++`), no back-references, at most 256 characters, and each pattern reads at most 1,024 characters of an entry. Every dependency scan is queued in the database before it is handed to the broker (`services/scan_queue.py`), and a scan task runs only from the queued state, so a scan handed over by both its caller and the beat dispatcher, or repeated while the queue is busy, clones once. The WS notification hub rejects over-capacity connections before the receive loop begins.

## Secrets and redaction

Runtime secrets (database and broker passwords, SMTP credentials, provider client secrets, Grype/Syft configuration on the operator side) live outside the database in `.env` / environment, and Compose requires the critical ones through `:?` guards. The UI container receives the built static image only and keeps the full `.env` inventory out of its runtime. Stored query strings, e-mail subjects, and error text redact credentials through `DEFAULT_SENSITIVE_KEYS` (which include `csrf`, tokens, signatures and authorisation values); clone/grype failures report commands with credentials masked; account e-mail rows validate through `_normalize_email` in `me.py`, and notification recipients resolve through the account's own verified rows.

Redaction is best effort: arbitrary prose, unknown key names and content embedded in URL paths may retain sensitive information. Configure additional sensitive keys via `OSPMAE_SENSITIVE_KEYS`, and keep secrets out of project descriptions, questions, manifest names and scan source labels.

## Provider diagnostics and logging

Request audit rows record client address, method, path, redacted query string, status and duration, with fixed caps (4096 query bytes, 256/512 user-agent/referer bytes), written off the event loop after the response. Requests from signed-in accounts are always recorded. Requests without an account carry no identity, so each client address (each IPv6 /64) adds at most 60 such rows a minute per API process, whatever their status: refusals, and public routes such as signing in; the allowance tracks at most 10,000 addresses at once and refuses to record new ones beyond that (it fails closed). Health checks, the method list a sign-in page reads and the navbar's unanswered-questions badge poll are not recorded. Rows are deleted after `OSPMAE_AUDIT_LOG_RETENTION_DAYS` (90 by default; 0 keeps them indefinitely).

**Accepted risk.** An attacker with many addresses can still add anonymous audit rows at 60 a minute per address per API process; the retention period bounds how long they stay, and recording them is what lets an operator see the attempt. KEEN applies the same allowance, counted across all its processes in Valkey. Each sign-in attempt also adds one `/action/sign-in` row recording its method and outcome (`security/audit.py`, ported from KEEN) and naming the account it reached, so an administrator can see which account is under attack; a name that matches no account is never stored, as it is often a password typed into the wrong field. Refusals by the sign-in limits add no such row, since their requests are already recorded within the audit allowance. Library wire/debug logging stays quiet by default: HTTPX and authlib warnings are the only expected console noise, and new dependency loggers must be reviewed before the app prints their request bodies.

## Deployment posture

The Compose files pin every third-party image by digest (`tools/docker_image_pins.py` keeps them current, with a nightly workflow proposing digest updates through reviewed pull requests). The API, worker and beat containers run as a non-root image user with every Linux capability dropped and `no-new-privileges`; the API's root filesystem is read-only. The API publishes no port: it is reached only through `component-ui`, whose nginx clears client-supplied identity headers, and it reports healthy (`/v1/system/health`) only after its migrations, which the worker and beat wait for. The worker, which clones and catalogues repositories named by project editors, runs under memory, processor and process-count limits (`OSPMAE_WORKER_MEM_LIMIT`, `OSPMAE_WORKER_CPUS`, 256 processes) with one task per process at a time and processes replaced every 100 tasks. The Compose network has a fixed subnet so that `OSPMAE_TRUSTED_PROXY_CIDRS` defaults to exactly the `component-ui` address and the network gateway (for a TLS proxy on the host), never a whole private range: a trusted peer can set forwarded addresses and, when enabled, the trusted identity header. PostgreSQL receives only its own settings, not the application `.env`; postgres and valkey hold their own startup ownership. Operators supply `.env` values for secrets, mail and provider settings; an enabled sign-in provider missing a required setting, such as its fixed `REDIRECT_URI`, refuses to start a sign-in and names the missing settings. Session identifiers and CSRF tokens are random values, not signed ones, so no signing key needs rotating. Application sessions are database-backed, so restoring a database copy restores authentication state; keep database and environment secrets (including `OSPMAE_MFA_ENCRYPTION_KEY`) protected together.

## Post-quantum cryptography

All OSPMAE browser, SMTP and provider traffic relies on TLS alone; its post-quantum posture follows whatever both ends negotiate. Database and broker connections within the Compose network share the deployment trust domain. Authentication factors are classical hashes; stored secrets (passwords, hashed tokens) keep their lifetime safety against quantum attacks because PBKDF2-SHA256 and SHA-256 stay outside the reach of shor-style algebraic attacks.
