# Security policy and threat model

## Reporting a vulnerability

Please report suspected vulnerabilities through this project's GitHub repository. Prefer **Security → Advisories → Report a vulnerability** for a private report. If private reporting is unavailable, open an issue asking for a private reporting channel and keep exploit details, credentials and sensitive data out of the public issue.

Every report must include a reproducible proof of concept demonstrating the issue. Include:

- The OSPMAE version or commit, deployment configuration relevant to the issue, and affected component.
- The attacker's required access, permissions and other prerequisites.
- Minimal reproduction steps or a script, expected and actual results, and evidence of the security impact.
- Synthetic test data and redacted logs or screenshots where useful.

Test on an installation you own or have explicit permission to assess. Use the smallest demonstration that establishes the issue, preserve other people's data, and avoid disruptive testing against public or hosted instances.

Our goal is to provide a preliminary response within **72 hours**. This is an acknowledgement and initial assessment target; investigation and remediation time depends on the report. OSPMAE offers **no monetary bounties**. Authors of validated reports will be credited, using their preferred name or handle, unless they request anonymity. We coordinate disclosure with reporters after assessing impact and remediation.

## Scope and trust boundaries

### What OSPMAE protects

OSPMAE stores the project catalogue: projects, releases, capability and framework mappings, manifests, dependency and vulnerability records, questions and subscriptions, plus user accounts and preferences. These records can carry an adopter's internal architecture or a maintainer's unreleased data, and several surfaces (draft releases, manifests, shared groups, subscription addresses) express who may read what. Security objectives include controlling who reads or changes each record, keeping scan credentials within their configured pipeline, preserving the integrity of dependency and vulnerability data once recorded, and maintaining service availability.

An OSPMAE installation is an organisational trust boundary. Users inside it receive access through roles, groups and permissions; project ownership (creator and owner groups) scopes writes for every account except administrators. Hosting mutually distrustful organisations requires isolated installations, databases and secrets.

### Actors

The threat model includes an unauthenticated Internet client, a malicious website visited by a signed-in user, a user acting beyond their assigned permissions, a project owner submitting hostile repository URLs or content, and hostile content returned by a configured release feed or package repository. A granted permission establishes who may act; reviewers still judge the truth of catalogue entries and scan results.

Application administrators are trusted to configure providers, permissions, feature switches and retention. Deployment operators control the executable code, database, broker and environment secrets. Compromise of these privileges can compromise the installation. An administrator's intended ability to delete data or grant permissions is part of that role; escaping the role's intended authority remains a security issue.

Upstream identity providers, Git hosts and package registries are trusted for their specific functions. A compromised provider can assert identities; a compromised Git host can return fabricated repository contents and observe the cloned content. The dependency host allowlist, per-request budgets and the scrubbed clone environment reduce the resulting exposure.

### Hostile scan inputs

A project's repository URL, lockfiles, package names, vulnerability titles and release feeds can all be attacker-shaped. The scan pipeline contains what such input can do to its own run: repository URLs validate against a host allowlist with credential and control-character refusals and never begin with `-` (the SSH `account@host:path` form is matched as a whole, so no part of it reads as a git option or transport), repository URLs hold no control character and write their scheme in lower case, so git is given exactly what was validated; a host allowlist that names no host allows none; every git command places `--` before the URL so git reads it as a repository whatever it holds, clones run in a fixed scrubbed environment with redirects disabled and positional (non-option) refs only, lockfile parsing reads at most the configured bytes per file and caps traversed and matched files, a lockfile's YAML is loaded without aliases and up to a fixed number of values, so a few hundred bytes cannot stand for a structure that takes seconds and megabytes to build; one scan stores at most 50,000 distinct dependencies and writes nothing when a repository lists more; identifiers taken from a repository or a scanner are stored without control characters and cut to their columns; feeds screen entity declarations across the whole bounded payload and the parser itself refuses a document type or entity declaration in any encoding (a UTF-16 feed spells one in bytes the screen does not match), one malformed lockfile or finding costs that item alone, and display values are cleaned before storage. Within those limits hostile input can still describe false dependencies or unsafe-looking findings; the catalogue marks their provenance through the recorded source files and commit, and reviewers or adopters verify before asserting anything downstream.

## Authentication

Signing in, sessions, second factors, single sign-on, CSRF and Origin checks, request limits, client addresses and the request audit trail come from MOSP, the framework OSPMAE shares with KEEN and MIDENA, so the three behave alike and a change to one of these rules is made there for all of them.

### Pages

nginx serves an application page only to a signed-in browser, as KEEN's does: each page request is first put to the API (`auth_request` to `/v1/auth/check`), so a signed-out browser receives the sign-in page in place of the page it asked for (status 403, at the same address, which a completed sign-in returns to). The administration page and its scripts are checked against `/v1/auth/check-admin` and answer 404 to any other account. The sign-in, second-factor and e-mail confirmation pages are served without a session; none holds account data. The gate keeps pages from signed-out browsers; every record is still authorised by the API.

### Sessions

Browser sessions use random, server-generated identifiers. Valkey keys each session by the SHA-256 digest of its identifier, so the store, its snapshot file and a client holding its password see no identifier a browser could present. The session cookie is HttpOnly, with `SameSite` and `Secure` from configuration. Where cookies are Secure and no cookie domain is set, the session, CSRF, device and pending second-factor cookies take the `__Host-` prefix (`__Host-ospmae_session`, `__Host-ospmae_csrf`), which a browser accepts only from the installation's own host over HTTPS, so a site on a sibling subdomain can neither set nor shadow them. Cookie names holding bytes outside printable ASCII are removed from every request, WebSocket handshakes included, before anything reads them, so a look-alike name cannot be read as one of these cookies.

Signing in issues a fresh identifier. Signing out is a POST carrying the session's CSRF token and deletes the session; when the store cannot confirm the deletion, sign-out answers with a retryable error and the browser keeps its cookies for the retry. A provider's session answers with the provider's end-session address. A session ends at its sliding expiry (`OSPMAE_SESSION_TTL_SECONDS`, 12 hours by default) and also a fixed time after sign-in (`OSPMAE_SESSION_MAX_AGE_SECONDS`, 30 days by default), whatever its sign-in method. A session opened through a provider ends while that provider is disabled.

Each session carries a snapshot of the account's role and permissions, checked against a database-backed authorisation version: every change to an account's role, groups or permissions, or to a group's role or permissions, moves the version of each account it affects, so open sessions follow. A password change or reset, a second-factor change and deactivation move the account's security version, which ends its sessions; a deactivated account's sessions stay ended if it is activated again. While Valkey is unavailable no session can be read, so authenticated requests are answered 503 with `Retry-After`.

### Sign-in throttling

Password sign-in follows the policy shared with KEEN and OSPMAE (`mosp.security.sign_in_throttle`), built on NIST SP 800-63B-4 section 3.2.2 and the OWASP device-cookie protocol:

- **Recognised browsers.** A browser that has given an account's correct password holds an HttpOnly, Secure, `SameSite=Strict` device cookie for that account, valid for 90 days and replaced at each correct password; Valkey holds only its digest, and an account keeps its 20 newest. Its attempts skip the per-address allowance and the account's throttle and draw on their own allowance: five wrong passwords in a row end its recognition.
- **Other browsers.** Attempts draw on a per-address allowance (`OSPMAE_LOGIN_RATE_LIMIT_PER_IP` in `OSPMAE_LOGIN_RATE_LIMIT_WINDOW_SECONDS`, 30 in five minutes by default, counting an IPv6 /64 network as one address) and on the account's throttle: five consecutive failures are free, each later attempt opens a wait of 30 seconds that doubles up to an hour, and after 100 consecutive failures other browsers are refused until a correct password from a recognised browser or an administrator's password reset. The throttle is keyed by a digest of the sign-in method and the compared username whether or not an account has it.
- **Refusals.** A held attempt is answered 429 with `Retry-After` and never reaches password verification. Every other rejection performs one full PBKDF2 verification (against a fixed dummy hash where no usable account exists), so response timing carries no account-existence signal. Sign-in limits fail closed while Valkey is unavailable.

**Accepted risk.** Someone who knows a username can make sign-in from browsers that have never signed in to that account wait up to an hour between attempts, and after 100 consecutive failures refuse them until recovery; recognised browsers keep signing in throughout, and an administrator can reset the password. A second factor covers a guessed password.

### Passwords and accounts

Passwords hash with PBKDF2-SHA256 at 600,000 iterations and per-password salts. New passwords follow NIST SP 800-63B-4: at least `OSPMAE_PASSWORD_MIN_LENGTH` characters (15; fewer, down to eight, only with `OSPMAE_MFA_POLICY=all`), at most 1,024, no composition rules, and a comparison with commonly guessed passwords, sequences and the account's own username. A username holds no control, format or line-break character, and no two accounts have names that differ only in case, width, spacing or invisible characters. Administrators create accounts, set their e-mail and reset passwords; there is no self-service reset by e-mail. A password change (`POST /v1/me/password`) re-verifies the current password under per-address and per-account (`OSPMAE_PASSWORD_CHANGE_RATE_LIMIT_PER_ACCOUNT`) allowances and ends every session of the account. An administrator's reset ends the account's sessions and every browser's recognition, clears its throttle and mails its owner.

The first administrator comes from `OSPMAE_BOOTSTRAP_ADMIN_USERNAME` and `OSPMAE_BOOTSTRAP_ADMIN_PASSWORD`, which take effect only while the users table is empty, under a database lock so concurrent API processes create one account. A placeholder or weak bootstrap password is refused, and the refusal never repeats the password.

### Second factors

Local accounts may enrol a TOTP authenticator, WebAuthn security keys or passkeys, or both, backed by ten single-use recovery codes stored as SHA-256 digests. `OSPMAE_MFA_POLICY` (`optional`, `admins`, `all`) decides whom the ceremony demands of. A second factor starts a five-minute challenge whose cookie is separate from the session cookie and dies with any account change. Each ceremony step checks `Origin` against `OSPMAE_PUBLIC_BASE_URL` and draws on per-address (40 in five minutes) and per-account (15 in five minutes) allowances; five wrong codes refuse every code for an hour, counted for a day after the latest wrong one. TOTP secrets are stored Fernet-encrypted under `OSPMAE_MFA_ENCRYPTION_KEY`. An enrolment change ends every other local session of the account. An operator recovers an account that has lost every factor with `scripts/mfa_admin.py` inside the API container (MOSP's `operator_reset`), which mails the owner a notice.

### Single sign-on and account linking

OpenID Connect providers and the bundled Google and GitHub support require an explicitly configured HTTPS redirect URI (plain HTTP only on localhost); the callback address never derives from a request host. Sign-in uses PKCE S256 and single-use server-side state with a 10-minute expiry, bound to the browser that started it by a host-bound cookie, so a callback link sent to someone else signs nobody in. ID tokens verify only under the asymmetric algorithms the deployment allows (`OSPMAE_OIDC_ALLOWED_ALGS`, RS256 by default; the token header cannot widen the list) and are validated for signature, issuer, a single audience equal to OSPMAE's client ID, authorised party, nonce, expiry and issued-at, with each claim of its expected type. Provider requests verify TLS, ignore proxy settings from the environment, follow no redirects, read uncompressed answers of at most 1 MiB, and end at a deadline. Single sign-on reaches existing accounts only: an account links a provider through an address it has proved by mailbox (`mosp.services.sso_emails`), the provider must report that address verified, and OSPMAE never creates accounts from provider claims. Session trust never derives from `preferred_username` or other selectable claims. The callback's query string is never stored in the audit log.

### Trusted remote-user authentication

`OSPMAE_TRUST_REMOTE_USER=true` hands authentication to the configured identity header, honoured only when the socket peer sits inside `OSPMAE_REMOTE_USER_TRUSTED_CIDRS` (a list separate from the forwarding proxies, with no default) and only for the single configured header name. The supplied nginx clears the client's copies of the identity headers authenticating proxies commonly use.

### Security notices and mail

The account's owner is mailed when something changes or tests the account's protection: a sign-in from an unfamiliar address, a password change or reset, a second factor added or removed, recovery codes replaced or used, a second-factor lockout, an operator's second-factor reset, and an SSO address verified or removed. Outgoing mail is two transactional outboxes, MOSP's security notices and OSPMAE's catalogue notices (new and draft releases, shared manifests, questions and replies): senders queue inside the transaction of the change they report and the worker drains both with backoff, recording only the exception class on failure and clearing a sent message's body, and a message's subject is kept on one line whatever the names in it hold. OSPMAE's spent messages are deleted after thirty days. The Administration page lists both outboxes, and each account sees what was mailed to it, without the bodies. Links in mail take their host from `OSPMAE_PUBLIC_BASE_URL` only, never from a request.

### Client addresses

`mosp.security.client_ip` resolves every client address (allowances, audit rows): it walks `X-Forwarded-For` right-to-left while each hop stays inside `OSPMAE_SECURITY_TRUSTED_PROXY_CIDRS` and keeps the socket peer otherwise. Allowance keys count one IPv4 address or one IPv6 /64 network. An untrusted client's forwarded headers cannot change its resolved address. The API reads no forwarded scheme or host: the public base URL names the installation's own origin.
## Authorisation

### Route policy

Every HTTP route passes one middleware decision (MOSP's route policy, with OSPMAE's routes declared in `app/security/route_policy.py` as `OSPMAE_POLICY`). The public routes are health, the root, and MOSP's sign-in, SSO and second-factor ceremonies. Every write is declared with what it needs: an account acting on its own records (preferences, shortcuts), a named permission (project, version, framework-mapping, capability and scan writes need `project.write`; framework writes `framework.write`; manifest exports and saves `manifest.export`; asking a question `project.question`), an object check the route itself performs (replies to questions, project subscriptions), or an administrator (every route under `/v1/admin/` apart from the audit and changelog readers, which `audittrail.read` also opens). OSPMAE closes every write it does not declare: such a route is refused for everyone, administrators included, so a new route fails closed until its rule is written. The test suite reconciles the policy with the routes the application serves.

### Catalogue access

Project ownership (the creator or a member of an owner group) object-scopes every account except administrators: a granted `project.write` changes only projects the account owns, so it widens nothing. A draft version is visible only to administrators, its project's creator and its owner groups, on every surface that reads versions (one rule, `security/project_access.py`): a route given a draft's id answers 404, exactly as for an id that does not exist, so ids say nothing about unpublished releases; the dependency directory lists no package that only drafts use and counts no draft; the same holds for the dependency lenses, the framework catalogue's project counts, a saved manifest's rows and exports (an item whose version is a draft the reader cannot view is left out), and a version's change history, which for other readers begins at publication. A scan is started by those who can edit the project (ownership and `project.write`), a running scan is not queued again beside itself, and what the last scan found stays readable until the new one replaces it. Why a scan failed (which can name the repository and quote the remote server) is read by the project's owners; other readers learn only that it failed, and a database or scanner error is stored by its kind alone. A question is answered by administrators and by holders of `project.answer` who own the project. A framework node that project versions map to is deleted, with those mappings, only on an explicit second request, as a framework is. Manifests grant read access through explicit owner and group membership; a manifest is placed in a group only by a member of it or an administrator. Subscription and question actions check ownership of the named objects.

### Roles, permissions and features

Accounts follow MOSP's model: an account is an administrator, an ordinary account, or takes its role from its groups (`inherit`); a group is an administrator group, an ordinary group, or carries no role. What an ordinary account may do comes from the permissions granted to it directly and through its groups: `project.write`, `framework.write`, `manifest.export`, `project.question`, `project.answer`, `project.diff` and `audittrail.read`. A job such as maintainer or architect is a set of these permissions, granted to a group. Administrators hold every permission. A change that would leave no active administrator, counting those who are administrators through a group, is refused under a lock that serialises such changes. The pages choose what to offer from the account's role and permissions; the API decides.

Feature switches (`core/features.py`: `frameworks`, `manifests`, `comparisons`, `questions`, `dependency_scans`, `release_feed`) turn optional areas off at the router level (HTTP 404), in Celery tasks (no-op when they run) and in startup seeding, so a disabled installation behaves like a small application: authentication, accounts, the project catalogue and the dependency and vulnerability dashboard stay. Administrators change them on the Administration page within the ceiling the deployment's `OSPMAE_FEATURE_*` settings set; each save is checked against the stored configuration version under a row lock (a stale save answers 409) and kept as a revision naming who saved it. Every request reads the stored version, so all API and worker processes apply a change at once.

### Scanning and dependencies

Dependency discovery enqueues per project version from explicit operator or project-owner actions; the clone host allowlist (`OSPMAE_DEPENDENCY_DISCOVERY_ALLOWED_HOSTS`, github/gitlab/codeberg by default) bounds clone destinations together with the URL validations above; clones cap their duration (`OSPMAE_DEPENDENCY_DISCOVERY_CLONE_TIMEOUT_SECONDS`) and traversal (`OSPMAE_DEPENDENCY_DISCOVERY_MAX_FILES`, `OSPMAE_DEPENDENCY_DISCOVERY_MAX_FILE_BYTES` per file), running grype/syft with configured paths and budgets. Discoveries exclude `.git`, build and vendored directories from traversal, skip symlinks, and clean displayed names/titles. Vulnerability records replay only through the recorded scanners; results stored for one version never name managed secrets, and clone errors echo credentials redacted (`mosp.security.redaction.redact_str`, which hides the userinfo of an address of any scheme and secret query values). Lockfiles and scanner output decode through `decode_json`, so one value nested past the interpreter's limit costs only itself.

A project that tracks a branch names it under the git ref-name rules (`depscan.scan.validate_git_ref_name`, which every ref reaching `ls-remote` or `clone` passes, a leading `-` included in its refusals), and its repository URL takes the same validation as version source links. The scan clones exactly that branch head, and a branch missing from the remote fails the scan with an error. Re-scans of one project run at most hourly; the beat poller claims each project through a compare-and-set on its last poll time, so overlapping beats queue a branch once.

A private repository's clones authenticate with one access token per project (`security/repo_credentials.py`). The token is write-only: the API stores it Fernet-encrypted under a key derived with HKDF from `OSPMAE_MFA_ENCRYPTION_KEY` for this purpose alone (so a stored TOTP secret and a stored token cannot stand in for one another), reports only whether one is saved, and keeps it out of responses, changelogs (which record only when a token was saved), audit rows and error text. Each token is bound to the one repository it was entered for (`repo_token_repository`, an HTTPS address on a host that passes the clone host allowlist): changing the repository needs the token entered again, and making the repository public deletes it. A private project lives in that repository. A version's source link and the tracked repository must be in it or the save is refused, a release the feed finds is always recorded there whatever the feed entry links to, and a clone of anything else is refused before git runs, so no editor and no feed can aim the token at another repository, including one the token could read. Addresses are compared as repositories: host and path without regard to case, without `.git`, and with a release, tag or tree page reduced to its repository. Git receives it only as an `Authorization` header scoped to the repository being cloned through `GIT_CONFIG_*` environment entries, never in a command line or URL, so it is never sent to another repository, another host, another port or over plain HTTP; a source URL elsewhere fails the scan before git runs. Tokens should still be read-only and scoped to that repository, so the forge enforces the same limit. Without a valid key, saving a token is refused; after the key changes, scans of private repositories fail until the token is entered again.

Release feeds fetch one bounded body per project on each beat poll, over HTTPS only. Each URL, and each redirect hop, is validated against every address its host resolves to (private, loopback, link-local, shared and other non-public ranges are refused), and the connection is then made to one of exactly those addresses (`security/outbound.py`), so a host whose name resolves differently a moment later cannot move the request to an internal address; TLS still names and verifies the original host. A feed is given 60 seconds in all, redirects included, as well as its size limit, which is applied to the decoded feed while it is decoded (a small compressed answer cannot expand past it; encodings other than gzip and deflate are refused), so a host that answers a little at a time cannot hold a worker; only entity-free XML is read. Release feed-derived versions inherit capability mappings only from existing published versions of the same project (a version the feed publishes never copies from a draft), carry labels of at most 64 characters, cap 10 new versions per cycle and 50 on a feed's first import, and stay consistent with the subscription notifications the project owner configured. Each project's feed is handled on its own: an entry that cannot be recorded costs that project's turn alone, and projects are polled least-recently-checked first, so one feed neither stops nor starves the others. For a private project, whose scans carry its access token, a feed entry never names the repository: every release is recorded in the one repository the token is bound to.

## Browser boundaries

### CSRF and Origin

Every unsafe request (POST, PUT, PATCH, DELETE) must come from OSPMAE's own origin: `Origin` must equal `OSPMAE_PUBLIC_BASE_URL`, and a write without `Origin` is refused, since every browser OSPMAE serves sends it. The origin check also covers sign-in and second-factor steps, which have no CSRF token yet. Every signed-in unsafe request also needs the CSRF header matching the CSRF cookie, and the token must be the one issued with the session, so another session's token or a cookie planted from a sibling site proves nothing. Notification WebSockets need the same origin and a signed-in session, are limited per user and per address, end when their session ends (checked at least every 30 seconds) and accept no frames larger than 1 KiB.

### Request limits

MOSP reads each request body in full, within 30 seconds, before any middleware or route sees it: credential forms take at most 16 KiB, second-factor ceremonies 256 KiB, and everything else 2 MiB (`app/mosp_hooks.body_limit`). JSON bodies must be standard JSON with finite numbers, at most 64 levels of nesting and at most 20,000 values; NUL characters, which PostgreSQL cannot store, become U+FFFD. Request targets carrying NUL, dot segments or encoded `/` or `\` are refused, since a crafted identifier could otherwise steer a page's own authenticated request to another route. Every integer in a path, query or body is bounded to PostgreSQL's integer range before it reaches a query, lists of node and project ids hold at most 2,000 entries, and a value the database still refuses is answered 400. Validation errors name invalid fields without echoing submitted values.

### Rendering, links and navigation

First-party JavaScript renders untrusted text through `escapeHtml` or `textContent`; the remaining HTML insertion sites are recorded and reviewed in `services/ui/tests/eslint-suppressions.json`, and the `no-unsanitized` lint rule refuses new ones. Links run through `safeExternalHref` in the design system and `safeHref` in OSPMAE pages, which drop script, data and other schemes, protocol-relative URLs, backslashes and control characters; `safeHref` applies the page's own rule whatever the design system's check says (that check can refuse more, never allow more) and percent-encodes the characters that could end an attribute. An organisation's website is stored only as a web address (`mosp.security.urls.external_url`). Post-authentication destinations are paths on OSPMAE's own site, validated through `same_site_path` on the server and the matching rule in the browser, which judges the path the URL parser resolves, so dot segments that resolve to `//host` are refused too. Stored navbar shortcuts are same-site paths without dot segments, or web addresses. Server values written into markup are escaped or coerced to numbers even where they are integers or fixed words today.

### Proxy, headers and caching

The supplied nginx adds the security-header set (X-Content-Type-Options, X-Frame-Options, Referrer-Policy `strict-origin-when-cross-origin`, COOP, HSTS, a `default-src 'self'` CSP with `script-src 'self'` and `img-src 'self' data: blob:`, and a Permissions-Policy denying camera, microphone and geolocation), refuses `//`-prefixed request targets, serves the API and its notification socket under `/api/` (passing the API the request target as the browser sent it, less the prefix, and refusing one that only normalises to `/api/`), clears client-supplied identity headers there, and marks every API response `no-store`. The API sets its own headers on every response, whatever proxy sits in front: `nosniff`, `X-Frame-Options: DENY`, cross-origin resource, opener and embedder policies, `no-store`, HSTS over HTTPS, and, on every response that sets no policy of its own, a CSP of `default-src 'none'; frame-ancestors 'none'; sandbox`, so an API answer opened directly runs nothing. The page check that nginx's `auth_request` reads names the account in a header, percent-encoding anything outside printable ASCII. The cache policy keeps third-party vendored assets immutable, HTML and first-party scripts fresh, and the design system revalidated before each use.

### Downloads and exports

Exports (Markdown manifests, XLSX and CSV comparison and dependency downloads, PDF reports generated in the browser) are attachments with fixed, escaped names whose plain file name is ASCII, with the full name in the encoded `filename*` form, and carry nothing beyond what the caller may read. Markdown export writes each cell as one line of plain text (line breaks flattened; emphasis, code, link, tag, entity and pipe characters escaped). Every text cell of a CSV or XLSX export passes MOSP's `spreadsheet_cell`, which neutralises a formula character (`=` `+` `-` `@`) at the start of a cell, after any characters importers skip, and after each semicolon, tab or line break, where a spreadsheet that splits on those starts a cell of its own; the browser's CSV export applies the same rule.

## Background work

Celery workers process scans, release feeds, tracked-branch re-scans (an hour apart at the shortest) and maintenance sweeps with per-task budgets: every task has a time limit (`OSPMAE_TASK_TIME_LIMIT_SECONDS`, with longer ones for scans and feed tasks), told to stop a minute before its process is replaced, so no input holds a worker without end. Past that soft limit every further database statement, outbound request and mail raises it again (`mosp.core.task_deadline`), and no handler in the task and scan code treats it as one input's failure, so a run stops where the limit falls; a scan stopped there is still recorded as stopped. Clones have timeouts, files byte caps and feeds size and time limits, and a beat-scheduled sweeper deletes expired sign-in states, second-factor challenges and SSO address proofs, and audit rows past `OSPMAE_AUDIT_LOG_RETENTION_DAYS` (90 by default); sessions, sign-in throttles and allowances live in Valkey and expire there. The git subprocess environment holds the credentials layer of its own path; clone children run with prompts, askpass helpers, system and global git configuration and HTTP redirects disabled, and the workers in general receive only the environment variables their configuration names. syft and grype are started outside the clone (both read a configuration file from their starting directory) with a fixed environment: their own settings, cache locations and proxy variables, and none of the worker's secrets. Release-feed ignore patterns are written by project editors and searched against text from upstream feeds, so regular expressions are refused when saved, and skipped when run, unless their backtracking stays bounded (`security/regex_shape.py`): no unbounded repeat inside another repeat, no variable repeat inside another whose rounds can match the same text, no repeated group whose alternatives can begin with the same character, no run of three or more adjacent repeats that can match the same character, no unbounded repeat of anything wider than one character unless possessive (`*+`, `++`), no back-references, at most 256 characters, and each pattern reads at most 1,024 characters of an entry. Whether two repeats can match the same text is judged on a fixed sample of characters plus every character and class range the pattern itself names, so the rules hold in any script, and a lookaround's repeats count with those around it. A project keeps at most 50 rules. The check is conservative and refuses some harmless patterns. As a second limit, each search of one text has a quarter of a second in the worker (`search_within`); a rule that reaches it is skipped and logged and not tried again in that run, and a project's rules together have five seconds of such stops per poll or first import, after which its remaining entries are taken without consulting them; so neither a pattern stored before these rules nor many slow ones can hold the worker. Every dependency scan is queued in the database before it is handed to the broker (`services/scan_queue.py`), and a scan task runs only from the queued state, so a scan handed over by both its caller and the beat dispatcher, or repeated while the queue is busy, clones once.

## Secrets, redaction and logging

Runtime secrets (database and broker passwords, SMTP credentials, provider client secrets, the second-factor encryption key, from which repository-token encryption is also derived) live in the environment, and Compose requires the critical ones through `:?` guards. The example environment file ships every credential empty, so an installation copied from it does not start until its own passwords are set. The UI container receives the built static image only. Stored query strings, referers and error text redact credentials through the shared sensitive-key list; clone and grype failures report commands with credentials masked. Configure further keys through `OSPMAE_SENSITIVE_KEYS`. Redaction is best effort: keep secrets out of project descriptions, questions, manifest names and scan source labels.

Request audit rows record client address, method, redacted path and query, status and duration, with fixed caps. Requests from signed-in accounts are always recorded; anonymous requests add at most 60 rows a minute per client address per API process. Each sign-in attempt adds one row naming the account it reached; a name matching no account is never stored. **Accepted risk:** an attacker with many addresses can still add anonymous audit rows at that rate; retention bounds how long they stay.

The health check and the navbar's unanswered-questions badge poll are not recorded.

## Deployment posture

The Compose file pins every third-party image by digest (`tools/docker_image_pins.py`, with a scheduled workflow proposing updates through reviewed pull requests), and the GitHub Actions workflows pin every third-party action by commit. The UI build installs packages with `npm ci --ignore-scripts`, pins the MOSP Design System by commit, and refuses a git package whose tree differs from the reviewed record in `services/ui/scripts/reviewed-git-packages.json`. The API, worker and beat containers run as a non-root user with every Linux capability dropped and `no-new-privileges`; the API's root filesystem is read-only. The API publishes no port and serves no schema or interactive documentation; it is reached through the UI container's nginx, and reports healthy (`/v1/system/health`) only after its migrations, which the worker and beat wait for. The worker, which clones and catalogues repositories named by project editors, runs under memory, processor and process-count limits (`OSPMAE_WORKER_MEM_LIMIT`, `OSPMAE_WORKER_CPUS`, 256 processes) with one task per process at a time and processes replaced every 100 tasks. The Compose network has a fixed subnet so the trusted-proxy list names exactly the proxy and the gateway. PostgreSQL receives only its own settings, not the application `.env`. Valkey is given its password in a configuration file written inside the container as it starts, so the password stays out of process arguments. The API image installs named syft and grype releases, each with the installer from that release's own tag and its signed checksums verified, and fails to build without `poetry.lock`; `.dockerignore` files keep `.env`, `.git` and test output out of the build contexts. Sessions live in Valkey and the second-factor key in the environment: keep the database, Valkey and environment secrets protected together.

## Post-quantum cryptography

Browser, SMTP, identity provider, Git host, package registry and release feed traffic relies on TLS alone; its post-quantum posture follows what both ends negotiate. Stored secrets are hashed with PBKDF2-SHA256 or SHA-256, or encrypted with Fernet (AES-128), whose symmetric strength Grover's algorithm halves without breaking.

## Required security review checklist

Reviewers check these boundaries after every round of changes and before a release. A green suite establishes only the behaviours it exercises. Record each applicable check's evidence, untested prerequisites and remaining limitations; do not mark an untested boundary as verified. Use synthetic credentials, local fixtures and disposable databases, and review the final working tree.

- **Account discovery and timing:** compare existing, absent, inactive and SSO-only accounts on sign-in, linking, manifest sharing and ownership changes. Check bodies, status codes and expensive operations as well as timing.
- **Route inventory:** every served route has a rule in `app/security/route_policy.py` or MOSP's policy; exercise permitted users, users without the permission, other owners, inactive accounts and anonymous callers, including adjacent paths, extra segments, wrong methods and encoded separators.
- **Catalogue visibility:** for each representation of a project version (detail, listings, dependency directory and lenses, framework counts, manifests and their exports, comparisons, changelog, questions, notifications), check that a reader who cannot see a draft learns nothing of it, and that ownership scopes every write for non-administrators.
- **Hostile scan inputs:** run hostile repository URLs (option-shaped, credential-bearing, control characters, SSH forms, other hosts), branch names, lockfiles (YAML aliases, deep nesting, oversized files, symlinks), scanner output and release feeds (DTDs, entities in UTF-16, oversized or slow answers, redirects to internal addresses) through save, scan, import and display.
- **CSRF, Origin and cookies:** cross-site GET and POST, missing and wrong tokens, another session's token, sibling-domain cookie injection, duplicate cookies.
- **Sessions, second factors and linking:** fixation, replay, concurrent revocation, deactivation and reactivation, pending-ceremony confusion, OIDC issuer, audience, nonce, PKCE and browser binding, and verified-address linking.
- **Outbound destinations:** identity provider, Git host and release feed requests keep their fixed or validated destinations, resolve and pin public addresses, refuse or bound redirects, ignore proxy environment variables, bound their answers and keep provider bodies out of errors; a private project's token reaches only its bound repository.
- **Resources:** body classes, JSON shape, integer and list bounds, feed and lockfile sizes, clone and scan time, regular expressions on the costliest accepted input at the largest accepted size.
- **Logs and redaction:** trace passwords, tokens, repository credentials and one-time links through URLs, referers, audit rows, errors, scan failures, mail and exports.
- **Supply chain:** image digests, action commits, the reviewed git-package tree and `--ignore-scripts` installs.
- **Class sweeps:** for each confirmed issue, record the property it violates, the search that found every path sharing it, and the contract test that enforces it across the codebase.

The full validation workflow uses PostgreSQL. jsdom page tests and mocked transports are focused checks with a narrower reach: real-browser rendering, the built Docker images, real scanner and Git host behaviour and resistance to sustained distributed attacks lie outside them, and need their own verification.
